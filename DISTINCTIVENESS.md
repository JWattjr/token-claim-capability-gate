# Distinctiveness: issuer disclosure-and-attestation protocol

This is a mechanism comparison, not an acceptance or points guarantee.
The original Portal objection is acknowledged: the previous contract and
Material Terms Change Guard both froze bounded items/evidence, independently
classified each, derived a deadline-governed status and persisted the result.

Reference acceptance/submission status is supplied review context, not independently
verified Portal status. Actual local reference implementations were inspected.
No changes were made to them.

| Mechanism | Material Terms Change Guard (accepted) | repair-refund-escrow (unsubmitted) | This release |
| --- | --- | --- | --- |
| Frozen subject | Baseline terms/categories and sources | Buyer/supplier criteria and allocations | Token claims, source URLs and power taxonomy |
| First judgment | Unchanged/adverse/beneficial/unclear terms | Buyer defect evidence support | Claim coherence; omitted material powers qualify claims |
| Responding party | No issuer-exclusive response stage | Supplier supplies repair versions | Appointed issuer alone submits disclosure URL |
| Carried obligation | No claim/power disclosure agenda | Criterion-specific repair issue history | Sorted immutable (claim_id, power) agenda locks review |
| Second judgment | No separate disclosure adequacy stage | Defect remedied or unresolved | Power-specific specificity AND source-code consistency |
| Output | Derived terms decision | Criterion-based release/refund accounting | Digest-bound disclosure attestation |
| Hard contradiction | Terms classification drives decision | Defect/repair drives settlement | BLOCKED final, cannot be cured by disclosure |
| Money settlement | No | Escrow settlement accounting | No funds or automatic listing |

Shared foundations remain: bounded frozen inputs, evidence interpretation,
independent exact validation, deterministic routing and deadlines. Repair escrow
also has the similar claim–remediate–rejudge shape; that shape itself is not
claimed as novel. This narrow obligation is disclosure of identified token powers,
not fixing an asset, transferring money or re-running the original judgment.
It is a reusable contract, not a frontend.
